# شرح واجهة البحث في سياسات الدعم

## المشروع بيعمل إيه؟
سؤال إنجليزي يدخل لواجهة FastAPI، يتقارن بعشر سياسات خيالية، ولو فيه نتيجة واضحة يرجع نص السياسة نفسه مع مرجعها. لو مفيش دليل كفاية يمتنع. ولو المستخدم طلب تنفيذ إجراء يرجعه للمسار الآمن، المشروع ما بيلغيش طلبات وما بيغيرش حسابات.

## مهم جدا: ده مش LLM
ده TF-IDF وcosine similarity مع قواعد توجيه واضحة. مفيش GPT ولا embedding model ولا vector database ولا agent مستقل. الميزة هنا سهولة التشغيل والاختبار وإثبات مصدر النص. العيب إنه بيعتمد على الكلمات وممكن يفشل مع إعادة صياغة أو يرجع سياسة مش مناسبة.

## مسار الكود
1. FastAPI وPydantic بيتأكدوا إن السؤال نص بطول من 3 لحد1000 حرف.
2. حارس أنماط بسيط يمنع بعض العبارات الواضحة. مش نظام أمان كامل وممكن يتجاوزوه.
3. أوامر زي إلغاء طلبي تروح handoff. مفيش تغيير خارجي.
4. TF-IDF يحول السؤال والوثائق لأوزان كلمات، وcosine يقيس التشابه.
5. حد أدنى وفرق بين النتيجتين يمنعوا إجابة ضعيفة أو ملتبسة.
6. الرد يرجع نص موجود فعلا، المرجع، النسخة، مسار التنفيذ ووقت التنفيذ.

## التقييم بصدق
12 اختبار نجحوا. في24 سؤال تجريبي مكتوبين للمشروع،23 رجعوا الحالة والمرجع المتوقعين. سؤال تتبع الشحنة امتنع بسبب تقارب سياستين وفضل موجود كحالة فشل. دي مش دقة مضمونة للعملاء، ومش مجموعة مستقلة كبيرة.

## أسئلة إنترفيو محتملة
- ليه TF-IDF قبل موديل مدفوع؟ عشان baseline يتقاس بسهولة من غير مفاتيح أو تكاليف.
- إيه الفرق بين similarity والثقة؟ التشابه رقم رياضي مش احتمال إن الإجابة صح.
- إزاي تطوره؟ مجموعة أسئلة مستقلة، embeddings ومقارنة baseline، reranker، صلاحيات ومراقبة وتنقيح بيانات، ثم توليد بإجابات موثقة لو فيه حاجة حقيقية ليه.
- هل الحارس يمنع prompt injection؟ لا. مجرد أمثلة قواعد والمشروع أصلا ماعندوش أدوات تغيّر أنظمة.

## تمرين عملي
أضف سياسة جديدة واختبار ليها. جرب سؤال غامض وسجل سبب الامتناع. اشرح الفشل الموجود بدل ما تخفيه. راجع `/docs` وجرب نوع بيانات غلط. قبل تقديم المشروع باسمك افهم الأجزاء وعدّل عليها فعلا، واذكر مساعدة AI. لا تدّعي خبرة إنتاج أو عميل حقيقي.
